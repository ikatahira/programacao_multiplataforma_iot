O que é Django?

Framework web em Python para quem tem prazos

📖 Definição

Django é um framework web de alto nível escrito em Python

O próprio Django se define como "um framework para perfeccionistas que têm prazos". Ele permite criar aplicações web completas com muito menos código, já que vem com soluções prontas para as tarefas mais comuns do desenvolvimento web.

🏗️ Arquitetura

MVT — Model, View, Template

Django usa o padrão MVT: o Model cuida do banco de dados, a View processa a lógica, e o Template renderiza o HTML para o usuário.

⚡ Fullstack

Front-end + Back-end juntos

Diferente de APIs REST, o Django pode renderizar páginas HTML completas, sendo uma solução fullstack — front e back no mesmo projeto.

✨ Por que usar Django?

Vantagens principais

Sintaxe simples ORM nativo Admin automático Segurança contra XSS/SQL Comunidade ativa Banco de dados integrado Código aberto desde 2005

💡 O que é Codespace?

Seu VS Code na nuvem

O GitHub Codespace é um ambiente de desenvolvimento completo que roda direto no navegador. Você tem acesso a um terminal Linux, editor VS Code e todos os recursos necessários — sem precisar configurar nada na sua máquina.

💡

Já fizemos isso antes! Na aula anterior já criamos nosso repositório no GitHub e abrimos um Codespace. Se precisar relembrar: repositório → botão verde Code → aba Codespaces → Create codespace on main.

📦 Passo 1 — Instalar Django

Instalando com pip

No terminal do Codespace, instale o Django e as dependências:

# Instalar Django

# Salvar as dependências

📌

Boa prática: sempre que instalar um novo pacote, rode pip freeze > requirements.txt para manter o arquivo atualizado. Isso garante que qualquer pessoa que abrir o projeto no Codespace consiga instalar tudo com um único comando.

O ponto . no final é importante! Sem ele, seria criada uma pasta dentro de outra pasta desnecessária.

Segurança — SECRET_KEY

Nunca suba segredos para o GitHub

⚠️ O problema

A SECRET_KEY não pode ficar exposta

Todo projeto Django tem uma chave secreta (SECRET_KEY) no settings.py. Se você subir esse arquivo para o GitHub, qualquer pessoa terá acesso a essa chave — o que é uma grave falha de segurança.

✅ A solução — python-dotenv

Usando variáveis de ambiente

  • Instalar python-dotenv 
    pip install python-dotenv
pip freeze > requirements.txt
  • Criar o arquivo .env na raiz do projeto 
    # .env — NUNCA suba este arquivo para o GitHub!
SECRET_KEY=sua-secret-key-aqui

    Copie a SECRET_KEY do seu settings.py e cole aqui.

  • Atualizar o settings.py 
    # setup/settings.py
from pathlib import Path
import os
from dotenv import load_dotenv

load_dotenv()

# Substitua a SECRET_KEY antiga por:
SECRET_KEY = str(os.getenv('SECRET_KEY'))
  • Criar o .gitignore

    Acesse gitignore.io, pesquise por "Django" e copie o conteúdo para um arquivo .gitignore na raiz do projeto. Isso garante que o .env e a pasta venv não vão para o GitHub.

🔐 Codespace Secrets

Alternativa: Secrets do Codespace

Uma forma ainda mais elegante no Codespace é usar os Secrets do GitHub. Vá em: Configurações do repositório → Secrets and variables → Codespaces → New repository secret. Crie um secret chamado SECRET_KEY com o valor da chave. O Codespace vai injetar automaticamente como variável de ambiente!

Arquivo requirements.txt

Registrando e reproduzindo dependências do projeto

❓ O que é

Por que o requirements.txt existe?

O requirements.txt é um arquivo de texto simples que lista todas as bibliotecas Python instaladas no projeto, com suas versões exatas. Ele garante que qualquer pessoa — ou qualquer ambiente (um novo Codespace, um servidor de produção, um colega de equipe) — consiga instalar exatamente as mesmas dependências com um único comando.

💡

Analogia: Pense no requirements.txt como a lista de ingredientes de uma receita. Sem ela, cada pessoa prepararia o projeto com versões diferentes das bibliotecas — e o resultado seria imprevisível.

⚙️ Como gerar

Comando pip freeze

O arquivo não é criado na mão. O pip gera automaticamente a partir do que está instalado no ambiente:

# Lista todos os pacotes instalados com versão exata
pip freeze

# Redireciona a saída para o arquivo requirements.txt
pip freeze > requirements.txt

O operador > redireciona a saída do terminal para dentro do arquivo. Se o arquivo não existir, ele é criado. Se já existir, é sobrescrito.

📄 Conteúdo do arquivo

O que aparece dentro do requirements.txt

Após instalar o Django e o python-dotenv, o arquivo terá um conteúdo parecido com este:

# requirements.txt gerado após: pip install django python-dotenv
asgiref==3.8.1
Django==5.0.6
python-dotenv==1.0.1
sqlparse==0.5.0

Cada linha segue o padrão pacote==versão. O == garante que a versão instalada será exatamente aquela, evitando incompatibilidades.

📦 Dependências indiretas

Por que aparecem mais pacotes do que os que eu instalei?

Quando você instala o Django, ele instala automaticamente pacotes dos quais depende — como asgiref e sqlparse. O pip freeze captura tudo que está no ambiente, incluindo essas dependências indiretas. Isso é intencional: garante reprodutibilidade total.

♻️ Reproduzindo o ambiente

Como instalar a partir do requirements.txt

Quando alguém clonar o repositório ou abrir um novo Codespace, basta rodar:

# Instala todas as dependências listadas no arquivo
pip install -r requirements.txt

A flag -r significa "leia as dependências a partir deste arquivo". Todos os pacotes serão instalados nas versões exatas especificadas.

🐙 GitHub

O requirements.txt deve ir para o repositório

Ao contrário do .env, o requirements.txt deve ser enviado para o GitHub. Ele não contém informações sensíveis e é fundamental para que o projeto funcione em outros ambientes.

📤 Commit e Push

Salvando as alterações no repositório

No Codespace, o repositório já está conectado ao GitHub. Para salvar, use o terminal ou a interface gráfica do VS Code:

# Verificar o que foi alterado
git status

# Adicionar todos os arquivos
git add .

# Criar um commit com mensagem descritiva
git commit -m "Aula 01: projeto Django criado com settings configurados"

# Enviar para o GitHub
git push
👀

Verifique no GitHub! Após o push, acesse seu repositório no GitHub e confirme que o arquivo .env NÃO aparece na lista de arquivos. Se aparecer, algo deu errado no .gitignore.
