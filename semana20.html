WebSocket e Dados em Tempo Real

Monte um servidor WebSocket em Node.js rodando junto do React no mesmo projeto StackBlitz (via proxy do Vite) e receba dados de sensores simulados ao vivo. Esta versão traz o passo a passo com mais detalhes, diagramas explicando cada conceito e checkpoints para conferir se está no caminho certo.

🎯 Objetivos de Aprendizagem

  • Entender a diferença entre polling HTTP e WebSocket para dados em tempo real;
  • Relacionar WebSocket com os conceitos de Sistemas Distribuídos da ementa (concorrência, comunicação assíncrona);
  • Criar um servidor WebSocket simples em Node.js, rodando dentro do mesmo projeto StackBlitz, que simula um sensor publicando dados;
  • Configurar o proxy do Vite para que servidor e front-end convivam no mesmo endereço público;
  • Conectar um componente React ao servidor e atualizar a tela em tempo real, sem recarregar a página;
  • Entender o papel de um broker de mensageria (introdução — será aprofundado no Módulo 06).
📖 Glossário desta semana — clique para expandir (19 termos)
WebSocket
Um protocolo que abre uma conexão persistente e bidirecional entre cliente e servidor, permitindo que o servidor envie dados a qualquer momento, sem o cliente precisar pedir.
handshake
O "aperto de mão" inicial entre cliente e servidor para abrir a conexão WebSocket, feito uma única vez no começo.
polling
Técnica em que o cliente pergunta ao servidor "tem novidade?" repetidamente, em vez de esperar o servidor avisar (usada na Semana 19).
Sistemas Distribuídos
Sistemas formados por vários programas/computadores separados que se comunicam entre si para funcionar como um todo (ex: sensor + servidor + dashboard).
concorrência
A capacidade de várias tarefas ou conexões acontecerem ao mesmo tempo dentro de um sistema, sem travar umas às outras.
broker de mensageria
Um servidor intermediário especializado em receber mensagens de quem publica (ex: sensores) e entregá-las para quem está interessado — será aprofundado no Módulo 06.
MQTT
Protocolo de mensageria leve, muito usado em IoT, baseado no padrão "publish/subscribe" — veremos em detalhe no Módulo 06.
proxy
Um "intermediário" que recebe uma requisição em um endereço e a repassa para outro endereço/porta por trás dos panos, sem o cliente perceber.
CORS
Cross-Origin Resource Sharing — uma regra de segurança do navegador que restringe requisições entre origens (domínios/portas) diferentes, a menos que o servidor autorize.
concurrently
Um pacote npm que permite rodar dois ou mais comandos/processos ao mesmo tempo em um único terminal.
localhost
O "endereço" que representa o próprio computador (ou, no nosso caso, o próprio ambiente virtual do WebContainer) — usado para processos se comunicarem entre si sem sair da máquina.
porta (port)
Um "número de canal" que identifica um serviço específico rodando em um computador/servidor — ex: a porta 8080 do nosso servidor WebSocket.
Web Serial API
Um recurso nativo do Chrome/Edge que permite que uma página web converse diretamente com um dispositivo USB (como um Arduino), sem instalar drivers nem programas.
baud rate
A velocidade de comunicação serial, medida em bits por segundo — o Arduino e o computador precisam usar o mesmo valor (ex: 115200) para se entenderem.
fototransistor
Um componente eletrônico que muda sua resistência elétrica de acordo com a quantidade de luz que recebe — é o "sensor de luz" físico usado no circuito desta aula.
escalabilidade horizontal
Aumentar a capacidade de um sistema adicionando mais instâncias/máquinas rodando em paralelo, em vez de deixar uma única máquina mais potente.
stateless
Um serviço que não guarda estado/memória entre requisições — cada requisição é independente, o que facilita rodar várias cópias em paralelo.
load balancer
Componente que distribui as requisições/conexões recebidas entre várias instâncias de um mesmo serviço, para nenhuma delas sobrecarregar.
EADDRINUSE
Erro do Node.js que significa "endereço/porta já em uso" — acontece quando você tenta iniciar um segundo servidor na mesma porta de um que já está rodando.

🧠 Por que WebSocket para IoT?

Na Semana 19 usamos polling: o cliente pergunta "tem novidade?" de tempos em tempos. Funciona, mas gasta banda e sempre tem atraso.

O WebSocket abre uma conexão persistente e bidirecional entre cliente e servidor: depois do handshake ("aperto de mão") inicial, os dois lados podem enviar mensagens a qualquer momento. Isso é exatamente o que sensores IoT precisam: assim que o ESP32 publica uma nova leitura, todos os painéis conectados recebem o dado imediatamente.

Esse padrão de "muitos dispositivos publicando e muitos clientes recebendo" é a essência de sistemas distribuídos com brokers de mensageria (MQTT, RabbitMQ, Kafka — Módulo 06, Semanas 28–32). Hoje construímos uma versão simplificada com WebSocket puro.

Figura 1 — no polling, o cliente puxa a informação repetidamente. No WebSocket, depois de um único handshake a conexão fica aberta, e o servidor empurra os dados assim que eles existem — sem atraso e sem desperdiçar requisições "vazias".

🧠 Discussão: isso escala?

O servidor.js que vamos construir guarda tudo em memória, em um único processo Node. Funciona perfeitamente para uma turma de 30 alunos testando em laboratório. Mas vale parar e pensar: e se fossem 10 mil sensores e 5 mil dashboards conectados ao mesmo tempo?

Alguns problemas apareceriam rapidamente:

  • Um processo só, um núcleo de CPU só — o Node é single-threaded para o código JavaScript; um único servidor não consegue processar dezenas de milhares de conexões simultâneas sozinho;
  • Estado em memória não é compartilhável — se você subir uma segunda instância do servidor para dividir a carga (escalabilidade horizontal, ou scale-out), cada instância teria seu próprio histórico de leituras, e um cliente conectado na instância A nunca veria os dados que chegaram na instância B;
  • Um serviço stateless escala melhor — se o servidor não guardasse nada localmente (o estado ficasse em um banco ou broker externo, compartilhado), poderíamos rodar 50 cópias idênticas dele atrás de um load balancer (balanceador de carga) sem esse problema.

É exatamente para resolver isso que existem os brokers de mensageria que veremos no Módulo 06: em vez de cada servidor guardar o histórico na própria memória, todos publicam e consomem de um broker central (ou de um cluster de brokers) — desacoplando "quem gera o dado" de "quantas instâncias estão de pé para atendê-lo". Guarde essa pergunta ("isso escala?") — ela vai voltar com respostas concretas nas Semanas 28–32.

Detalhe importante do ambiente: como estamos num navegador sem instalação local, vamos rodar o servidor e o front-end dentro do mesmo projeto StackBlitz, usando um único endereço exposto. Isso evita o problema de portas/URLs diferentes não conseguirem "se enxergar". A técnica usada — proxy do Vite — é a mesma usada em empresas reais para evitar problemas de CORS entre front-end e back-end durante o desenvolvimento.

🛠️ Passo a Passo — Servidor WebSocket + Cliente React no mesmo projeto

1 Reabra o projeto e instale as bibliotecas necessárias

No StackBlitz, projeto dashboard-iot-isw044, abra a aba Terminal (ou TERMINAL, se já estiver no editor "nova geração" ligado ao GitHub) e rode:

npm install ws concurrently

ws é a biblioteca de WebSocket para Node.js. concurrently permite rodar dois comandos (o servidor e o Vite) ao mesmo tempo com um único npm run dev.

✅ Como saber que deu certo: o terminal mostra added 2 packages (ou similar) sem nenhuma linha vermelha de erro, e o prompt volta a ficar vazio.
2 Verifique o tipo de módulo do projeto

Abra o arquivo package.json na raiz do projeto e veja se existe a linha "type": "module". Os templates atuais de Vite + React no StackBlitz normalmente já vêm assim. Isso significa que arquivos .js na raiz usam a sintaxe moderna import/export (e não require).

Se não existir essa linha: adicione "type": "module", logo abaixo da linha "name": ... e salve. Sem ela, o comando node servidor.js do próximo passo vai falhar com "Cannot use import statement outside a module".
3 Crie o servidor que simula um sensor

No explorador de arquivos, clique com o botão direito na raiz do projeto (não dentro de src — o servidor não faz parte do código que o Vite empacota, e por isso continua sendo um arquivo .js puro, sem TypeScript) → New file → servidor.js:

import { WebSocketServer } from 'ws';

const wss = new WebSocketServer({ port: 8080 });
console.log('Servidor WebSocket rodando na porta 8080');

wss.on('connection', (socket) => {
  console.log('Novo cliente conectado. Total:', wss.clients.size);

  const intervalo = setInterval(() => {
    const leitura = {
      sensor: 'temperatura',
      valor: (20 + Math.random() * 10).toFixed(1),
      timestamp: new Date().toISOString(),
    };
    socket.send(JSON.stringify(leitura));
  }, 2000);

  socket.on('close', () => {
    clearInterval(intervalo);
    console.log('Cliente desconectado');
  });
});

Repare que este arquivo não leva // @ts-nocheck: ele roda direto pelo Node (node servidor.js), fora do processo de build do Vite/React, então as regras de TypeScript dos outros arquivos do curso não se aplicam aqui.

Erros comuns nesta etapa:
  • "Cannot use import statement outside a module" → falta "type": "module" no package.json (veja o passo anterior);
  • "Error: listen EADDRINUSE: address already in use :::8080" → já existe um servidor.js rodando na mesma porta. Pare o processo antigo no terminal com Ctrl+C antes de rodar de novo.
4 Configure o proxy no vite.config.ts

Abra vite.config.ts na raiz e adicione a seção server.proxy, sem apagar o bloco test que você já configurou na Semana 18 para o Vitest:

/// <reference types="vitest/config" />
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
  },
  server: {
    proxy: {
      '/ws': {
        target: 'ws://localhost:8080',
        ws: true,
      },
    },
  },
})

Isso diz ao Vite: "toda vez que o navegador tentar abrir um WebSocket no caminho /ws, encaminhe essa conexão para o processo que está escutando na porta 8080" — mesmo que, para o navegador, tudo pareça vir do mesmo endereço único do Preview.

Figura 2 — o proxy faz o front-end (Vite) e o back-end (servidor.js) parecerem "um só" para o navegador, mesmo rodando como dois processos Node separados dentro do mesmo WebContainer.

Abra package.json e localize a seção "scripts". Troque a linha "dev" por:

No terminal, pare o processo atual se estiver rodando (clique no terminal e pressione Ctrl+C) e rode:

Você deve ver, no mesmo terminal, tanto a mensagem Servidor WebSocket rodando na porta 8080 quanto o log normal do Vite — os dois processos rodando lado a lado dentro do mesmo container.

✅ Como saber que deu certo: no terminal aparecem duas seções distintas (geralmente coloridas de forma diferente pelo concurrently, com prefixos como [0] e [1]): uma com Servidor WebSocket rodando na porta 8080, outra com VITE ready in ...ms. Se só uma delas aparecer, o outro processo travou — role o terminal para cima em busca de erro.
6 Conectando o React ao WebSocket via o caminho /ws

Crie src/useWebSocket.ts (sem JSX, por isso a extensão .ts):

// @ts-nocheck
import { useState, useEffect, useRef } from 'react';

function useWebSocket() {
  const [ultimaLeitura, setUltimaLeitura] = useState(null);
  const [conectado, setConectado] = useState(false);
  const socketRef = useRef(null);

  useEffect(() => {
    const protocolo = window.location.protocol === 'https:' ? 'wss://' : 'ws://';
    const url = protocolo + window.location.host + '/ws';
    const socket = new WebSocket(url);
    socketRef.current = socket;

    socket.onopen = () => setConectado(true);

    socket.onmessage = (evento) => {
      const dado = JSON.parse(evento.data);
      setUltimaLeitura(dado);
    };

    socket.onclose = () => setConectado(false);
    socket.onerror = (err) => console.error('Erro no WebSocket:', err);

    return () => socket.close();
  }, []);

  return { ultimaLeitura, conectado };
}

export default useWebSocket;
Por que window.location.host em vez de "localhost:8080" fixo? No StackBlitz (e em qualquer ambiente hospedado), o endereço público do seu Preview não é literalmente localhost — é uma URL gerada dinamicamente. Usar window.location.host faz o código funcionar tanto no StackBlitz quanto, futuramente, em um computador local ou em produção, sem precisar trocar nada.
7 Exibindo o dado em tempo real

Crie src/SensorAoVivo.tsx:

// @ts-nocheck
import useWebSocket from './useWebSocket';

function SensorAoVivo() {
  const { ultimaLeitura, conectado } = useWebSocket();

  return (
    <div style={{ padding: 20, border: '1px solid #333', borderRadius: 10 }}>
      <p>Status: {conectado ? '🟢 conectado' : '🔴 desconectado'}</p>
      {ultimaLeitura ? (
        <>
          <h2>{ultimaLeitura.valor} °C</h2>
          <small>Atualizado em {new Date(ultimaLeitura.timestamp).toLocaleTimeString()}</small>
        </>

        <p>Aguardando primeira leitura...</p>
      )}
    </div>
  );

export default SensorAoVivo;

Use este componente em App.tsx (mesmo processo das semanas anteriores: import SensorAoVivo from './SensorAoVivo'; function App() { return <SensorAoVivo />; }) e abra o Preview: o valor da temperatura deve mudar sozinho a cada 2 segundos.

Figura 3 — assim como o setInterval das semanas anteriores, o return () => socket.close() dentro do useEffect é essencial: sem ele, cada remontagem do componente abriria uma nova conexão sem fechar a anterior.

✅ Como saber que deu certo: o Preview mostra "Status: 🟢 conectado" e um valor de temperatura que muda sozinho a cada 2 segundos, junto com o horário da última atualização (ex: "Atualizado em 14:32:10").
Não conectou? Clique no botão de abrir o Preview em uma aba nova do navegador (ícone de seta/quadrado no canto do painel de Preview do StackBlitz) em vez de deixar só no iframe embutido — em alguns casos o WebSocket dentro do iframe do editor tem restrições extras, e a aba separada resolve. Se "Status" ficar travado em "🔴 desconectado", confira também se o servidor.js ainda está rodando (volte ao terminal) e se o vite.config.ts foi salvo corretamente com o bloco server.proxy.
8 Mantendo um histórico de leituras

Em useWebSocket.ts, adicione um novo estado e troque o onmessage:

const [historico, setHistorico] = useState([]);

socket.onmessage = (evento) => {
  const dado = JSON.parse(evento.data);
  setUltimaLeitura(dado);
  setHistorico(anterior => [...anterior.slice(-19), dado]); // mantém só as últimas 20 leituras
};

// não esqueça de devolver o histórico também:
return { ultimaLeitura, historico, conectado };
Por que slice(-19)? Sem limitar o tamanho do array, um dashboard ligado por horas acumularia milhares de itens em memória. slice(-19) pega só os últimos 19 itens do array atual; somando o item novo que está sendo adicionado, o resultado sempre tem no máximo 20 leituras.
✅ Como saber que deu certo: se você renderizar historico.length na tela, o número cresce a cada 2 segundos até chegar em 20 — e a partir daí permanece fixo em 20, mesmo com o tempo passando, porque os itens mais antigos vão sendo descartados.

🔌 Bônus: Conectando um Sensor Real via Web Serial API

Até aqui, o "sensor" era simulado com Math.random(). Se o seu laboratório já tem um Arduino Uno com um sensor de luz montado, dá para trocar o dado simulado por um dado 100% real — e, o melhor, sem instalar absolutamente nada, usando a Web Serial API: um recurso do próprio navegador que lê a porta USB do Arduino diretamente da aba do Chrome/Edge.

📦 Projeto de referência: "Magnificent Hango" — Sensor de Luz Ambiente

Este é um circuito real de exemplo, com Arduino Uno, um fototransistor (sensor de luz) e um LED indicador. Existem duas montagens possíveis, que invertem a lógica do sinal:

  • Circuito 1 — HIGH ao detectar luz: o pino do sensor vai para nível alto quando há luz incidindo no fototransistor;
  • Circuito 2 — HIGH ao não detectar luz: a mesma lógica, só que com o fototransistor e o resistor de 10 kΩ trocados de posição no divisor de tensão, invertendo o sinal.

Lista de materiais (BOM) do projeto: 2× Arduino Uno R3, 2× LED branco, 2× LED azul, resistores de 180 Ω, 300 Ω e 10 kΩ, e 2× fototransistores. 📄 baixar bom-sensor-luz.csv · 📐 baixar esquemático em PDF.

1 Entenda o firmware já gravado no Arduino

O sketch abaixo já está preparado para os dois circuitos (a diferença é só um parâmetro). Ele lê o pino digital do sensor a cada 50 ms e imprime o estado pela porta Serial:

#define IR_SENSOR 2
#define LED       3

void setup() {
  pinMode(IR_SENSOR, INPUT);
  pinMode(LED, OUTPUT);
  Serial.begin(115200);
}

void print_stateled(const bool beam, const bool inverted) {
  Serial.print("State[");
  Serial.print(beam ? "High" : "Low");
  Serial.print("]");
  if (inverted) {
    Serial.println(beam ? "Feixe detectado" : "Feixe interrompido");
  } else {
    Serial.println(beam ? "Feixe interrompido" : "Feixe detectado");
  }
}

void loop() {
  const bool beamDetected = digitalRead(IR_SENSOR);
  digitalWrite(LED, beamDetected);
  print_stateled(beamDetected, 1); // troque para 0 no circuito 2
  delay(50);
}

Cada linha impressa na Serial fica assim: State[High]Feixe detectado — exatamente o texto que vamos capturar e transformar em dado utilizável no dashboard.

Quem grava o programa no Arduino? Gravar (fazer upload) um sketch exige o Arduino IDE ou o Arduino Web Editor, o que normalmente é preparado com antecedência pelo professor/técnico do laboratório — já que instalar softwares pode exigir permissões que vocês não têm. A parte que não exige nenhuma instalação, e que faremos agora, é ler os dados de um Arduino que já está com o programa gravado, usando apenas o navegador.

📥 Arquivos completos: magnificent_hango1.ino (circuito 1) e magnificent_hango2.ino (circuito 2).

2 Conecte o Arduino ao computador do laboratório

Conecte o cabo USB do Arduino Uno a uma porta USB do computador — isso não exige instalação de driver no Windows 11 (o Arduino Uno usa um chip USB-Serial já reconhecido nativamente pelo sistema na grande maioria dos casos).

3 Abra o Preview em uma aba separada do navegador

A Web Serial API só funciona em uma página real do Chrome/Edge, não dentro do iframe do editor do StackBlitz. Clique no ícone de "abrir em nova aba" no canto do painel de Preview antes de continuar.

4 Crie o hook useSerialSensor

De volta ao editor, crie src/useSerialSensor.ts:

// @ts-nocheck
import { useState, useRef, useCallback } from 'react';

function useSerialSensor(baudRate = 115200) {
  const [leitura, setLeitura] = useState(null);
  const [conectado, setConectado] = useState(false);
  const suportado = 'serial' in navigator;
  const portRef = useRef(null);

  const conectar = useCallback(async () => {
    if (!suportado) return;

    const port = await navigator.serial.requestPort(); // abre o seletor de porta do navegador
    await port.open({ baudRate });
    portRef.current = port;
    setConectado(true);

    const decoder = new TextDecoderStream();
    port.readable.pipeTo(decoder.writable);
    const reader = decoder.readable.getReader();

    let buffer = '';
    while (true) {
      const { value, done } = await reader.read();
      if (done) break;
      buffer += value;

      let indice;
      while ((indice = buffer.indexOf('\n')) >= 0) {
        const linha = buffer.slice(0, indice).trim();
        buffer = buffer.slice(indice + 1);

        const match = linha.match(/State\[(High|Low)\](.+)/);
        if (match) {
          setLeitura({
            estadoPino: match[1],       // "High" ou "Low"
            mensagem: match[2].trim(),  // "Feixe detectado" ou "Feixe interrompido"
            timestamp: new Date().toISOString(),
          });
        }
      }
    }
  }, [baudRate, suportado]);

  return { leitura, conectado, suportado, conectar };
}

export default useSerialSensor;
Por que precisa de um clique para conectar? Por segurança, o navegador só mostra o seletor de portas (requestPort()) em resposta a uma ação explícita do usuário, como clicar em um botão — nunca automaticamente ao carregar a página.
5 Exibindo a leitura real

Crie src/SensorReal.tsx:

// @ts-nocheck
import useSerialSensor from './useSerialSensor';

function SensorReal() {
  const { leitura, conectado, suportado, conectar } = useSerialSensor();

  if (!suportado) {
    return <p>⚠️ Seu navegador não suporta Web Serial API. Use Chrome ou Edge no computador.</p>;
  }

  return (
    <div style={{ padding: 20, border: '1px solid #333', borderRadius: 10 }}>
      {!conectado && (
        <button onClick={conectar}>🔌 Conectar Arduino</button>
      )}
      {conectado && leitura && (
        <>
          <h2>{leitura.mensagem}</h2>
          <small>Pino: {leitura.estadoPino} · {new Date(leitura.timestamp).toLocaleTimeString()}</small>
        </>
      )}
    </div>
  );
}

export default SensorReal;

Clique em "Conectar Arduino", escolha a porta na janela que o navegador abrir (algo como "USB Serial Device (COMx)") e cubra/descubra o sensor com a mão: a mensagem deve alternar entre "Feixe detectado" e "Feixe interrompido" em tempo real.

✅ Como saber que deu certo: ao clicar em "Conectar Arduino", o navegador abre uma janela nativa listando as portas USB disponíveis. Depois de escolher a porta certa e clicar em "Connect", o botão desaparece e é substituído pela mensagem do sensor, que muda ao vivo conforme você tampa/destampa o fototransistor com a mão.
Erros comuns nesta etapa:
  • Nenhuma porta aparece na janela do navegador → confira se o cabo USB está bem conectado e se é um cabo de dados (alguns cabos USB são só de carga, sem os pinos de dados);
  • O botão "⚠️ Seu navegador não suporta..." aparece mesmo no Chrome/Edge → confirme se está na aba separada do passo 3, e não dentro do iframe do editor do StackBlitz — a Web Serial API é bloqueada dentro de iframes por segurança;
  • Conecta mas a mensagem nunca muda → confira se o parâmetro inverted no firmware (print_stateled(beamDetected, 1)) bate com o circuito físico realmente montado (1 para o Circuito 1, 0 para o Circuito 2).
6 Uma limitação importante (e uma boa discussão de Sistemas Distribuídos)

Diferente do servidor WebSocket simulado (que qualquer pessoa na rede pode acessar), a Web Serial API só funciona na aba do navegador fisicamente conectada ao Arduino via USB — os outros colegas não conseguem ver esses dados direto. Isso não é uma falha do que construímos: é assim que hardware físico funciona na prática. Para "distribuir" essa leitura para outras pessoas/telas, seria necessário um broker de mensageria — exatamente o papel que MQTT, RabbitMQ e Kafka cumprem, e que veremos em detalhe no Módulo 06 (Semanas 28–32).

Testar WebSocket de verdade em unidade é complexo — a prática comum é criar um mock da classe WebSocket global e simular eventos onmessage manualmente, verificando se o estado do componente atualiza como esperado. Documente no README como você testaria isso (não é obrigatório implementar o mock completo esta semana).
Esboço de como seria esse mock (para referência futura, não precisa rodar esta semana): criar uma classe MockWebSocket com os mesmos métodos (send, close) e propriedades de evento (onopen, onmessage) do WebSocket real, substituir global.WebSocket por ela no teste, renderizar o componente, chamar manualmente instancia.onmessage({'{ data: JSON.stringify(...) }'}) e verificar se o texto esperado aparece na tela — o mesmo princípio do vi.fn() usado para simular o fetch na Semana 19.
