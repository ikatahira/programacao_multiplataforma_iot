Consumo de APIs REST no Front-end

Continuando no mesmo projeto StackBlitz: use fetch, trate carregamento/erro, crie um hook useFetch reutilizável e dê os primeiros passos em GraphQL. Esta versão traz o passo a passo com mais detalhes, diagramas explicando cada conceito e checkpoints para conferir se está no caminho certo.

🎯 Objetivos de Aprendizagem

  • Revisar os conceitos de API REST: recursos, verbos HTTP, status codes e JSON;
  • Consumir uma API pública real dentro de um componente React com fetch;
  • Tratar corretamente os três estados de uma requisição assíncrona: carregando, erro e sucesso;
  • Criar um hook customizado (useFetch) para reaproveitar lógica de requisição entre componentes diferentes;
  • Implementar atualização periódica (polling) combinando useEffect e setInterval;
  • Comparar rapidamente REST com GraphQL, conforme previsto na ementa da disciplina;
  • Escrever um teste automatizado que simula (mock) a função fetch, sem depender de internet.
📖 Glossário desta semana — clique para expandir (14 termos)
API
Application Programming Interface — um "conjunto de portas de entrada" que um sistema oferece para que outros programas troquem dados com ele.
API REST
Um estilo de API muito comum na web, onde cada informação é um "recurso" acessado por uma URL, usando verbos HTTP (GET, POST, etc).
endpoint
O endereço (URL) específico de uma API que você chama para obter ou enviar um dado — ex: /forecast, /usuarios/1.
verbo HTTP
A "ação" de uma requisição HTTP: GET (buscar), POST (criar), PUT/PATCH (atualizar), DELETE (remover).
JSON
JavaScript Object Notation — um formato de texto simples e legível para representar dados estruturados, usado pela maioria das APIs.
status code
Um número que a API devolve junto da resposta, indicando se deu certo (200), se foi criado (201), se o pedido está errado (400) ou se algo falhou no servidor (500).
fetch
Função nativa do JavaScript usada para fazer requisições HTTP (buscar dados de uma API) direto do navegador.
Promise
Um objeto do JavaScript que representa uma operação assíncrona (que leva um tempo para terminar, como uma requisição de rede) e seu resultado futuro.
hook customizado
Uma função criada por você (não pronta do React) que começa com "use" e reaproveita lógica com estado/efeitos entre vários componentes.
polling
Técnica em que o cliente pergunta ao servidor "tem novidade?" repetidamente, de tempos em tempos, em vez de esperar o servidor avisar.
GraphQL
Uma alternativa a REST onde o cliente pede exatamente os campos que quer, em uma única requisição, em vez de receber tudo que o endpoint devolve.
mock
Uma versão "falsa"/simulada de algo (como a função fetch) usada em testes, para não depender de internet ou de um servidor real.
CORS
Cross-Origin Resource Sharing — mecanismo de segurança do navegador que decide se um site pode ou não buscar dados de outro domínio diferente.
race condition
Bug causado pela ordem imprevisível de operações assíncronas — ex: uma requisição antiga "chega" depois de uma mais nova e sobrescreve o dado certo com um errado.

🧠 Revisão rápida: REST em uma página

Uma API REST expõe recursos através de URLs, e você interage com eles usando verbos HTTP:

  • GET — buscar dados (ex: última leitura de um sensor)
  • POST — criar um novo registro (ex: o ESP32 envia uma nova leitura)
  • PUT/PATCH — atualizar um registro existente
  • DELETE — remover um registro

As respostas normalmente vêm em JSON e trazem um status code: 200 OK, 201 criado, 400 erro do cliente, 404 não encontrado, 500 erro no servidor.

Figura 1 — ciclo básico de uma chamada REST: seu componente React pede um recurso por URL, o servidor responde com um status code (200 = deu certo) e um corpo em JSON, que você usa para montar a tela.

3 Criando o componente com fetch()

De volta ao StackBlitz, crie o arquivo src/PainelClima.tsx (botão direito em src → New file — mesmo processo da Semana 18):

// @ts-nocheck
import { useState, useEffect } from 'react';

function PainelClima() {
  const [dados, setDados] = useState(null);
  const [carregando, setCarregando] = useState(true);
  const [erro, setErro] = useState(null);

  useEffect(() => {
    const url = 'https://api.open-meteo.com/v1/forecast?latitude=-22.97&longitude=-49.87&current=temperature_2m,relative_humidity_2m,wind_speed_10m';

    fetch(url)
      .then(resposta => {
        if (!resposta.ok) throw new Error('Falha na requisição: ' + resposta.status);
        return resposta.json();
      })
      .then(json => {
        setDados(json.current);
        setCarregando(false);
      })
      .catch(err => {
        setErro(err.message);
        setCarregando(false);
      });
  }, []);

  if (carregando) return <p>Carregando dados do sensor climático...</p>;
  if (erro) return <p>Erro ao buscar dados: {erro}</p>;

  return (
    <div>
      <h2>Estação Climática</h2>
      <p>🌡️ Temperatura: {dados.temperature_2m} °C</p>
      <p>💧 Umidade: {dados.relative_humidity_2m}%</p>
      <p>🌬️ Vento: {dados.wind_speed_10m} km/h</p>
    </div>
  );
}

export default PainelClima;

Importe e use em App.tsx (pode substituir todo o conteúdo do arquivo por isso, já que o painel de sensores da Semana 18 continua salvo no histórico do Git, se quiser recuperar depois):

}
export default App;

Olhe o painel de Preview: em poucos segundos o texto "Carregando dados do sensor climático..." deve virar os dados reais de temperatura vindos da internet — algo como "🌡️ Temperatura: 24.3 °C".

Por que os três estados (carregando / erro / dados)? Numa aplicação real conectada a sensores, a rede pode cair, o servidor pode demorar, o sensor pode estar offline. Tratar esses três casos desde já evita uma tela em branco quando algo falhar.

Figura 2 — os três estados nunca coexistem: o componente começa em "carregando", e assim que o fetch termina (com sucesso ou falha), o React re-renderiza mostrando ou os dados ou a mensagem de erro — nunca as duas coisas juntas.

✅ Como saber que deu certo: o Preview mostra, por alguns instantes, "Carregando dados do sensor climático..." e depois troca sozinho para o painel completo — título "Estação Climática" e algo como "🌡️ Temperatura: 21.6 °C", "💧 Umidade: 97%", "🌬️ Vento: 11.3 km/h" (os números variam conforme o clima real da sua região no momento).
Erros comuns nesta etapa:
  • "Erro ao buscar dados: Falha na requisição: 400" → normalmente é a URL malformada. Confira se o parâmetro está escrito ¤t= (E comercial normal) e não ¤t= — esse símbolo de moeda aparece quando um & seguido de "current" é colado de uma fonte que não escapou o caractere corretamente. Reescreva a linha da URL manualmente se precisar, comparando com o exemplo do Passo 2;
  • "Cannot read properties of null (reading 'temperature_2m')" → o componente tentou renderizar dados.temperature_2m antes da requisição terminar. Confira se os if (carregando) return ... e if (erro) return ... estão antes do return principal, na ordem certa;
  • Preview fica travado para sempre em "Carregando..." → normalmente é if (!resposta.ok) não tratado corretamente, ou a URL foi digitada com erro de sintaxe. Abra o Console do navegador (F12) e procure por mensagens em vermelho;
  • Esqueceu o array de dependências [] no final do useEffect → o componente entra em loop, disparando uma requisição nova a cada re-renderização (sintoma: a aba do navegador trava ou o terminal mostra muitas linhas repetidas rapidamente).
4 Criando um hook customizado — useFetch

Crie src/useFetch.ts (esse arquivo não tem JSX, por isso a extensão é .ts em vez de .tsx):

Como criar o arquivo no StackBlitz: clique com o botão direito na pasta src no Explorer (não na raiz do projeto) → New File → digite exatamente useFetch.ts (atenção: extensão .ts, não .tsx) → Enter → cole o código abaixo → salve com Ctrl+S. Se o arquivo não aparecer na árvore depois, confira se ele não foi criado na pasta errada (fora de src) ou se esqueceu de salvar.
// @ts-nocheck
import { useState, useEffect } from 'react';

function useFetch(url) {
  const [dados, setDados] = useState(null);
  const [carregando, setCarregando] = useState(true);
  const [erro, setErro] = useState(null);

  useEffect(() => {
    setCarregando(true);
    fetch(url)
      .then(r => {
        if (!r.ok) throw new Error('HTTP ' + r.status);
        return r.json();
      })
      .then(json => { setDados(json); setCarregando(false); })
      .catch(err => { setErro(err.message); setCarregando(false); });
  }, [url]);

  return { dados, carregando, erro };
}

export default useFetch;

Agora PainelClima.tsx fica muito mais simples:

// @ts-nocheck
import useFetch from './useFetch';

function PainelClima() {
  const url = 'https://api.open-meteo.com/v1/forecast?latitude=-22.97&longitude=-49.87&current=temperature_2m,relative_humidity_2m,wind_speed_10m';
  const { dados, carregando, erro } = useFetch(url);

  if (carregando) return <p>Carregando...</p>;
  if (erro) return <p>Erro: {erro}</p>;

  return (
    <div>
      <p>🌡️ {dados.current.temperature_2m} °C</p>
      <p>💧 {dados.current.relative_humidity_2m}%</p>
    </div>
  );
}
export default PainelClima;
Repare na diferença: como o useFetch agora devolve o JSON inteiro (não só o campo current, como fazíamos antes), o acesso muda de dados.temperature_2m para dados.current.temperature_2m. É um detalhe fácil de esquecer ao migrar código antigo para o hook novo.

Nesse ponto, a estrutura de arquivos dentro de src/ deve ter ficado assim — um componente simples (App.tsx) chamando o painel, e o painel usando o hook:

src/
├── App.tsx          → importa e renderiza <PainelClima />
├── PainelClima.tsx  → usa o hook useFetch(url) e exibe os dados
├── useFetch.ts      → a lógica reaproveitável de busca (criada agora)
└── SensorCard.tsx   → componente da Semana 18 (pode conviver com o novo)
Vite recarrega sozinho ao salvar (Hot Reload): depois de criar o useFetch.ts e salvar as alterações em PainelClima.tsx, você pode reparar no terminal algo como:

Isso é o Hot Reload do Vite funcionando: qualquer arquivo salvo dentro de src/ (ou o próprio vite.config.ts) faz o servidor de desenvolvimento reiniciar ou atualizar a prévia automaticamente. Você não precisa parar o npm run dev e rodar de novo — só salvar o arquivo já é suficiente, e o painel à direita atualiza os valores de Temperatura/Umidade sozinho, como no exemplo abaixo.

✅ Como saber que deu certo: o Preview continua mostrando os mesmos dados de antes (temperatura e umidade), só que agora o código de PainelClima.tsx ficou bem mais curto — toda a lógica de fetch/estado saiu para dentro do useFetch.
Erro comum: esquecer de trocar dados.temperature_2m para dados.current.temperature_2m ao migrar para o hook — o erro no console costuma ser "Cannot read properties of undefined", porque dados.temperature_2m não existe mais nesse formato (o hook devolve o JSON completo, com o campo current por dentro).
5 Atualização periódica (polling)

Sensores de verdade mudam de valor com o tempo. Vamos fazer o useFetch repetir a busca automaticamente, sem precisar recarregar a página. Edite src/useFetch.ts, trocando o useEffect por este:

useEffect(() => {
  function buscar() {
    fetch(url)
      .then(r => {
        if (!r.ok) throw new Error('HTTP ' + r.status);
        return r.json();
      })
      .then(json => { setDados(json); setCarregando(false); })
      .catch(err => { setErro(err.message); setCarregando(false); });
  }

  buscar(); // primeira busca, imediata
  const id = setInterval(buscar, 60000); // repete a cada 60 segundos
  return () => clearInterval(id); // limpeza ao desmontar
}, [url]);
Isso é polling: o cliente pergunta ao servidor de tempos em tempos, exatamente como fizemos na Semana 18 com o setInterval simulando sensores. Na Semana 20 veremos o WebSocket, onde é o servidor quem avisa o cliente assim que há um dado novo, sem precisar ficar perguntando.

Figura 4 — o retorno da função dentro do useEffect (return () => clearInterval(id)) continua sendo essencial: sem ela, cada vez que o componente remonta cria um intervalo novo, empilhando requisições desnecessárias.

✅ Como saber que deu certo: abra o Console do navegador (F12 → Network → filtro "Fetch/XHR") e deixe a página aberta por mais de 1 minuto — deve aparecer uma nova requisição para api.open-meteo.com a cada 60 segundos, sem você precisar recarregar a página.
Erro comum: esquecer o return () => clearInterval(id) — sem ele, toda vez que o componente for remontado (por exemplo, ao editar e salvar o código durante o desenvolvimento) um novo intervalo é criado por cima do antigo, e depois de algumas edições a página passa a fazer 2, 3, 4 requisições simultâneas ao mesmo tempo.
6 Bônus — um gostinho de GraphQL

A ementa também cita GraphQL. Diferença central: em REST você recebe tudo que o endpoint devolve; em GraphQL você pede exatamente os campos que quer. Para testar rapidamente, sem precisar mexer no projeto, abra o Console do navegador em qualquer aba (tecla F12 → aba Console) e cole:

fetch('https://countries.trevorblades.com/', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    query: `{ country(code: "BR") { name capital currency } }`
  })
})
  .then(r => r.json())
  .then(json => console.log(json.data.country));

Repare que a requisição é sempre um POST, e o "pedido" de dados vai dentro do corpo (query), como se fosse um texto — bem diferente da URL com parâmetros que usamos no REST. O resultado aparece no próprio Console, com só os três campos pedidos (name, capital, currency), nada a mais.

🧪 Checkpoint TDD — testando o useFetch sem depender de internet

No terminal do StackBlitz (o mesmo Vitest já configurado na Semana 18, com environment: 'jsdom' no vite.config.ts), crie o arquivo src/useFetch.test.ts:

// @ts-nocheck
import { test, expect, vi } from 'vitest';

global.fetch = vi.fn(() =>
  Promise.resolve({
    ok: true,
    json: () => Promise.resolve({ current: { temperature_2m: 25 } }),
  })
);

test('useFetch busca e devolve os dados simulados', async () => {
  const resposta = await global.fetch('url-qualquer');
  const json = await resposta.json();
  expect(json.current.temperature_2m).toBe(25);
});

Aqui, vi.fn(...) cria uma mock — uma versão "de mentirinha" da função fetch global, que sempre devolve o mesmo JSON fixo (temperature_2m: 25), sem fazer nenhuma requisição de verdade. Isso deixa o teste rápido e confiável: ele não depende da internet estar disponível, nem do clima real da sua cidade mudar o resultado.

Próximo passo natural (opcional): em vez de testar o fetch isoladamente como acima, dá para importar o hook useFetch de verdade e renderizar um componente que o usa, junto com @testing-library/react — exatamente como fizemos com o SensorCard na Semana 18 — para confirmar que o texto "25" aparece na tela depois do mock resolver.
✅ Como saber que deu certo: rode npx vitest run no terminal — deve aparecer ✓ useFetch busca e devolve os dados simulados em verde, sem nenhuma requisição real de rede sendo feita (você pode até desligar o Wi-Fi para confirmar que o teste continua passando).

🌐 Painel de Dados Externos

Construa um painel que consome uma API pública real, tratando corretamente carregamento e erros.

📋 Instruções:

  1. Escolha uma API pública gratuita e sem necessidade de chave (Open-Meteo, ViaCEP, ou outra API REST livre à sua escolha);
  2. Implemente o hook useFetch reutilizável, conforme o passo a passo;
  3. Exiba os dados em pelo menos 2 componentes diferentes, reaproveitando o mesmo hook (ex: um painel de clima e um painel de CEP/endereço);
  4. Trate os três estados: carregando, erro (force um erro trocando a URL propositalmente, por exemplo com um CEP inválido ou uma latitude/longitude quebrada) e sucesso;
  5. Implemente atualização automática (polling) a cada 30–60 segundos em pelo menos um dos painéis;
  6. Escreva ao menos 1 teste automatizado mockando o fetch, como no Checkpoint TDD acima;
  7. Salve as alterações no mesmo repositório GitHub (botão Commit, no topo do editor).
🌟 Desafio opcional:
  • Adicione um botão "Atualizar agora" que chama a mesma função de busca do polling, sem esperar os 60 segundos;
  • Mostre a hora da última atualização bem-sucedida na tela (ex: "Última atualização: 14:32:10").
📦 Entregável: Link do repositório atualizado + print mostrando o estado de erro funcionando corretamente.

✅ Critérios de Avaliação:

  • Hook customizado funcional e reaproveitado em mais de um componente
  • Tratamento visível de carregando/erro/sucesso
  • Atualização periódica implementada corretamente (sem vazamento de intervalos)
  • Teste automatizado presente
  • Organização do código e histórico de commits
