📚 Conteúdo Teórico

Introdução: Por que gerência de projetos importa

Desenvolver software multiplataforma envolve times, prazos e integrações complexas entre frontend, backend e dispositivos IoT. Sem uma forma organizada de planejar, acompanhar e entregar o trabalho, mesmo um bom código técnico pode resultar em um projeto atrasado, mal escopado ou sem comunicação entre a equipe. É exatamente esse o papel da gerência de projetos, citada no objetivo geral da ementa da disciplina.

O gerenciamento tradicional (cascata) planeja tudo antecipadamente e executa em fases sequenciais rígidas. Já as metodologias ágeis — o foco desta aula — trabalham em ciclos curtos e iterativos, entregando valor continuamente e se adaptando a mudanças.

1. O Manifesto Ágil

Publicado em 2001, o Manifesto para Desenvolvimento Ágil de Software estabelece quatro valores centrais:

  • Indivíduos e interações mais que processos e ferramentas
  • Software em funcionamento mais que documentação abrangente
  • Colaboração com o cliente mais que negociação de contratos
  • Responder a mudanças mais que seguir um plano fixo

Esses valores deram origem a frameworks como Scrum, Kanban, XP (Extreme Programming) — os dois primeiros detalhados a seguir.

2. Scrum

O Scrum organiza o trabalho em ciclos curtos chamados Sprints (geralmente de 1 a 4 semanas), com papéis, eventos e artefatos bem definidos.

👤 Product Owner

Representa o cliente/usuário. Prioriza o que deve ser feito através do Backlog do Produto.

🧭 Scrum Master

Facilita o processo, remove impedimentos e garante que o time siga o framework.

👥 Development Team

Equipe multidisciplinar responsável por transformar itens do backlog em incrementos funcionais.

Eventos do Scrum

  • Sprint Planning: reunião no início da sprint para definir o que será entregue.
  • Daily Scrum: reunião diária de ~15 min ("o que fiz ontem, o que farei hoje, quais bloqueios eu tenho").
  • Sprint Review: apresentação do incremento pronto ao final da sprint.
  • Sprint Retrospective: reflexão do time sobre o que funcionou e o que pode melhorar.

Artefatos

  • Product Backlog: lista priorizada de tudo que o produto precisa (funcionalidades, correções, melhorias)
  • Sprint Backlog: itens selecionados do backlog para a sprint atual
  • Incremento: a soma de todos os itens concluídos, em estado utilizável

3. Kanban

O Kanban é um método visual de gestão de fluxo de trabalho, baseado em um quadro dividido em colunas que representam os estágios do trabalho. Diferente do Scrum, não trabalha com sprints fixas — o fluxo é contínuo, e o foco está em limitar o WIP (Work In Progress / trabalho em andamento) para evitar sobrecarga da equipe.

Configurar broker MQTT

Scrum x Kanban — quando usar cada um?

  • Scrum: bom para projetos com entregas planejadas em ciclos (ex.: o Projeto Integrador da Semana 40, com entregas parciais até a apresentação final).
  • Kanban: bom para fluxo contínuo de manutenção/suporte, ou para equipes pequenas que preferem simplicidade sem cerimônias fixas.

4. Gamificação aplicada a projetos e ao ensino

Gamificação é o uso de elementos de jogos (pontos, níveis, badges, rankings, desafios) em contextos que não são jogos, para aumentar engajamento e motivação. Na disciplina, isso aparece como forma de tornar o aprendizado de programação multiplataforma mais dinâmico — por exemplo, badges por semana concluída, pontuação por desafios extras resolvidos, ou rankings colaborativos entre equipes no projeto integrador.

Em times reais de desenvolvimento, gamificação também é usada para incentivar boas práticas: cobertura de testes, revisão de código (code review) e cumprimento de prazos.

5. Coding Dojo

O Coding Dojo é uma prática de aprendizado coletivo de programação, onde um grupo resolve um problema de código junto, em um ambiente colaborativo e sem julgamento — focado em aprender fazendo. O formato mais comum é o Randori:

  • Um "piloto" e um "copiloto" programam juntos em frente ao grupo (pair programming ao vivo)
  • A cada rodada (5-10 min), o piloto vira plateia e outra dupla assume
  • O problema costuma ser resolvido com TDD (Red, Green, Refactor — já estudado no Módulo 8), reforçando a prática de escrever o teste antes do código
  • Todo o grupo participa ativamente, sugerindo abordagens e discutindo soluções

O Coding Dojo combina, na prática, três elementos já vistos na ementa: gerência de projetos colaborativa, TDD e gamificação (já que costuma ser estruturado como um desafio em grupo com tempo limitado).

Ferramentas de apoio

  • GitHub Projects — quadro Kanban integrado ao repositório, ideal para o projeto da disciplina
  • Trello — quadro Kanban simples e visual
  • Jira — ferramenta profissional de Scrum/Kanban usada amplamente no mercado

💪 Atividades Práticas

📝 Atividade 1: Backlog do Projeto Integrador

Monte o Product Backlog do seu Projeto Integrador (Semana 40) usando os princípios do Scrum.

📋 Instruções:

  1. Liste todas as funcionalidades necessárias (IoT, backend/broker, web, mobile)
  2. Escreva cada item como uma User Story ("Como [usuário], quero [funcionalidade], para [benefício]")
  3. Priorize os itens (Alta / Média / Baixa)
  4. Divida o backlog em pelo menos 2 sprints até a apresentação final
📦 Entregável: Backlog documentado (planilha ou GitHub Projects) + print das sprints planejadas

✅ Critérios de Avaliação:

  • User stories bem escritas e completas
  • Priorização coerente com o escopo do projeto
  • Distribuição realista entre as sprints

📌 Atividade 2: Quadro Kanban no GitHub Projects

Configure um quadro Kanban real para acompanhar o desenvolvimento da equipe.

📋 Instruções:

  1. Crie um board no GitHub Projects vinculado ao repositório do projeto
  2. Defina as colunas: A Fazer, Em Andamento, Em Revisão, Concluído
  3. Defina um limite de WIP para a coluna "Em Andamento"
  4. Migre os itens do backlog da Atividade 1 para o quadro
  5. Atualize o quadro conforme a equipe avança no projeto ao longo do semestre
📦 Entregável: Link do board + print do quadro em uso

✅ Critérios de Avaliação:

  • Board configurado corretamente
  • Uso consistente ao longo do desenvolvimento
  • Limite de WIP respeitado

🥋 Atividade 3: Coding Dojo em Grupo (Randori + TDD)

Participe de uma sessão de Coding Dojo resolvendo um pequeno desafio de código coletivamente, aplicando TDD.

📋 Instruções:

  1. Forme grupos de 5-6 alunos
  2. Escolha um desafio simples (ex.: validar dados de um sensor, converter unidades de temperatura)
  3. Siga o formato Randori: piloto + copiloto por 5-7 minutos, depois troca
  4. Escreva sempre o teste antes do código (Red, Green, Refactor)
  5. Ao final, discuta em grupo o que foi aprendido com a dinâmica
📦 Entregável: Código-fonte final da sessão + breve relato da experiência do grupo

✅ Critérios de Avaliação:

  • Participação de todos os membros como piloto/copiloto
  • Ciclo TDD respeitado (teste antes do código)
  • Qualidade da reflexão final sobre a dinâmica
