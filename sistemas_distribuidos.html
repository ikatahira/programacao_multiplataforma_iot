📖 Fundamentos de Sistemas Distribuídos

Leia com calma — os laboratórios a seguir vão testar exatamente o que está aqui.

O que é um sistema distribuído?

Um sistema distribuído é um conjunto de computadores independentes que se apresenta ao usuário como um único sistema coerente. No projeto integrador desta disciplina isso é literal: dispositivos ESP32/Arduino, backend, broker de mensageria, banco de dados e apps web/mobile/desktop rodam em máquinas diferentes, mas precisam se comportar como um sistema único e confiável.

⚡ Concorrência

É a capacidade de um sistema lidar com múltiplas tarefas progredindo no mesmo intervalo de tempo — diferente de paralelismo, que exige múltiplos núcleos executando literalmente ao mesmo tempo. Concorrência pode ocorrer até em um único núcleo, alternando rapidamente entre tarefas (é o que faz o event loop do Node.js).

  • Processo: unidade independente de execução, com seu próprio espaço de memória.
  • Thread: unidade de execução dentro de um processo, compartilhando memória com as demais — mais leve, porém mais arriscada.
  • Condição de corrida (race condition): ocorre quando duas execuções acessam e modificam o mesmo dado compartilhado ao mesmo tempo, e o resultado passa a depender da ordem imprevisível de execução.
🎯 EXEMPLO REALJá tentou pegar um cupom de desconto limitado ou comprar um produto em "oferta relâmpago" e a compra deu erro mesmo o produto aparecendo disponível? Provavelmente foi uma condição de corrida: várias pessoas tentaram reservar o mesmo estoque ao mesmo tempo, e o sistema não bloqueou o registro rápido o suficiente.

A defesa clássica contra isso é o lock / mutex: uma região crítica só pode ser acessada por uma execução de cada vez.

// Mutex simples via encadeamento de Promises (JavaScript)
class Mutex {
  constructor(){ this._p = Promise.resolve(); }
  lock(){
    let resolveLock;
    const lockPromise = new Promise(res => resolveLock = res);
    const willLock = this._p.then(() => resolveLock);
    this._p = this._p.then(() => lockPromise);
    return willLock; // retorna a função "unlock"
  }
}

🔓 Openness

Um sistema é aberto quando expõe suas interfaces através de padrões documentados e independentes de fornecedor, permitindo que qualquer cliente compatível se conecte a ele — mesmo construído por outra equipe, em outra linguagem.

  • Protocolos abertos: HTTP/REST, MQTT, WebSocket — todos com especificação pública.
  • Formatos abertos: JSON, XML — em vez de formatos binários proprietários.
  • APIs documentadas: OpenAPI/Swagger, permitindo que web, mobile e desktop consumam o mesmo backend.

O oposto disso é o vendor lock-in: depender de um único fornecedor, o que trava a evolução do sistema.

🎯 EXEMPLO REALO PIX é aberto: qualquer banco ou fintech (Nubank, Itaú, PicPay...) pode implementar o protocolo e conversar entre si. Já o iMessage da Apple é fechado: só funciona entre iPhones, e por isso quem tem iPhone às vezes vê mensagens de amigos com Android aparecerem em verde, fora do sistema — um exemplo clássico de falta de openness entre plataformas.

📈 Escalabilidade

É a capacidade de um sistema continuar respondendo bem mesmo quando a carga cresce (mais usuários, mais sensores, mais dados).

  • Vertical (scale up): aumentar os recursos de uma única máquina. Simples, mas com limite físico.
  • Horizontal (scale out): adicionar mais máquinas trabalhando juntas — é como Kafka e RabbitMQ escalam em cluster.
  • Sharding: dividir os dados entre vários nós.
  • Cache distribuído: reduzir a carga no banco principal.
  • Replicação: manter cópias dos dados em múltiplos nós para disponibilidade.

Teorema CAP: em sistemas distribuídos não é possível garantir simultaneamente Consistência, Disponibilidade e Tolerância a Partições — é preciso escolher trade-offs. Um sistema de monitoramento IoT, por exemplo, costuma priorizar disponibilidade em vez de consistência absoluta.

🎯 EXEMPLO REALServiços de streaming e redes sociais reforçam sua infraestrutura em datas de pico previsíveis — estreia de temporada, Black Friday, virada de ano — justamente para evitar quedas. Quando isso falha (como aconteceu com sites de venda de ingressos em lançamentos de shows muito concorridos), o sistema simplesmente não aguenta o volume de acessos simultâneos.

--- rodando de novo, três vezes seguidas: sempre 1 ---
SEM protecao -> contador final = 1
SEM protecao -> contador final = 1


    

      Por que o JavaScript sempre dá 1? Nas outras linguagens, threads reais são pausadas em momentos aleatórios pelo sistema operacional — por isso o número perdido varia. Em JavaScript, as 100 chamadas começam todas antes de qualquer uma chegar no primeiro await — então todas leem o contador em 0, e todas escrevem 1 de volta. Perda de 99%, sempre, de forma 100% repetível.
      


      Esses três códigos (mais um devcontainer.json pronto pra GitHub Codespaces e um workflow de GitHub Actions que roda tudo automaticamente a cada push) estão disponíveis pra qualquer aluno reproduzir — é só pedir ao professor o pacote race-demo-isw044.zip, subir num repositório novo e abrir em Code → Codespaces → Create codespace.
