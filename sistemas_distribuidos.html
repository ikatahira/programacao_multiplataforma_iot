📚 Conteúdo Teórico

Introdução: O que é um Sistema Distribuído?

Um sistema distribuído é um conjunto de computadores independentes que se apresenta ao usuário como um único sistema coerente. Em um projeto multiplataforma com IoT — como o projeto integrador desta disciplina — isso é exatamente o que acontece: dispositivos ESP32/Arduino, um backend, um broker de mensageria, um banco de dados e aplicações web/mobile/desktop, todos rodando em máquinas diferentes, precisam se comportar como um sistema único e confiável.

Segundo a literatura clássica (Tanenbaum & Van Steen), um sistema distribuído é caracterizado por algumas propriedades centrais — três delas são explicitamente citadas na ementa da disciplina: concorrência, openness e escalabilidade.

⚡ Concorrência

Múltiplos componentes executam e acessam recursos compartilhados ao mesmo tempo, sem que um processo precise esperar o outro terminar.

🔓 Openness

O sistema é construído sobre padrões e interfaces abertas, permitindo que componentes heterogêneos e de fornecedores diferentes se comuniquem.

📈 Escalabilidade

O sistema continua funcionando de forma eficiente conforme o número de usuários, dispositivos ou volume de dados cresce.

1. Concorrência

Concorrência é a capacidade de um sistema lidar com múltiplas tarefas progredindo dentro do mesmo intervalo de tempo. É diferente de paralelismo, que exige múltiplos núcleos executando instruções literalmente ao mesmo tempo — a concorrência pode ocorrer até em um único núcleo, através de alternância rápida entre tarefas (como faz o event loop do Node.js).

Processos vs. Threads

  • Processo: unidade independente de execução, com seu próprio espaço de memória.
  • Thread: unidade de execução dentro de um processo, compartilhando memória com as demais threads do mesmo processo — mais leve, porém mais arriscada.

Condição de corrida (Race Condition)

Ocorre quando duas ou mais threads/processos acessam e modificam o mesmo dado compartilhado simultaneamente, e o resultado final depende da ordem imprevisível de execução. É um dos bugs mais difíceis de reproduzir e depurar em sistemas distribuídos — imagine dois sensores IoT tentando gravar no mesmo registro do banco de dados ao mesmo tempo.

Estratégias comuns para evitar isso incluem locks/mutex (região crítica exclusiva), semáforos, filas de mensageria (que serializam o processamento) e modelos assíncronos não bloqueantes, como o usado em Node.js.

Exemplo — Concorrência em Node.js (assíncrono)

// Múltiplas leituras de sensores IoT em paralelo, sem bloquear o event loop
async function lerTodosSensores(sensores) {
  const leituras = await Promise.all(
    sensores.map((sensor) => lerSensor(sensor))
  );
  return leituras;
}

async function lerSensor(sensor) {
  const resposta = await fetch(`http://broker.local/sensores/${sensor.id}`);
  return resposta.json();
}

Exemplo — Concorrência em Python (threading vs. multiprocessing)

import threading

def processar_leitura(id_sensor):
    print(f"Processando dados do sensor {id_sensor}")

threads = []
for i in range(5):
    t = threading.Thread(target=processar_leitura, args=(i,))
    threads.append(t)
    t.start()

for t in threads:
    t.join()  # aguarda todas as threads terminarem

Em Python, o GIL (Global Interpreter Lock) limita a execução real em paralelo de threads Python puras — por isso, tarefas que exigem muito processamento costumam usar multiprocessing em vez de threading.

2. Openness (Abertura)

Um sistema é considerado aberto quando expõe suas interfaces através de padrões documentados e independentes de fornecedor, permitindo que qualquer cliente compatível se conecte a ele — mesmo que tenha sido construído por outra equipe, em outra linguagem.

  • Protocolos abertos já usados no curso: HTTP/REST, MQTT, WebSocket — todos com especificações públicas.
  • Formatos abertos: JSON, XML — em vez de formatos binários proprietários.
  • APIs documentadas: Swagger/OpenAPI, permitindo que qualquer plataforma (web, mobile, desktop) consuma o mesmo backend.
  • Interoperabilidade: um sensor ESP32 publicando em um broker MQTT não precisa "saber" se quem vai consumir aquele dado é um app React Native, um dashboard React ou um app Electron — o protocolo aberto garante essa desacoplagem.

O oposto da openness são sistemas proprietários/fechados, que travam o desenvolvedor a um único fornecedor (vendor lock-in) e dificultam a integração entre plataformas — exatamente o problema que a disciplina busca evitar ao ensinar múltiplas plataformas integradas por protocolos abertos.

3. Escalabilidade

Escalabilidade é a capacidade de um sistema continuar respondendo bem mesmo quando a carga (usuários, dispositivos IoT, volume de mensagens) aumenta.

Escalabilidade Vertical x Horizontal

  • Vertical (scale up): aumentar os recursos de uma única máquina (mais CPU, RAM). Simples, mas tem limite físico.
  • Horizontal (scale out): adicionar mais máquinas/instâncias trabalhando em conjunto. É a abordagem usada por brokers como Kafka e RabbitMQ em cluster.

Técnicas comuns

  • Load balancing: distribuir requisições entre várias instâncias do backend.
  • Sharding/Particionamento: dividir os dados entre vários bancos/nós (o Kafka, visto no Módulo 6, particiona tópicos justamente por isso).
  • Cache distribuído: reduzir a carga no banco de dados principal (Redis, por exemplo).
  • Replicação: manter cópias dos dados em múltiplos nós para disponibilidade.

Teorema CAP

Em sistemas distribuídos escaláveis, o Teorema CAP afirma que não é possível garantir simultaneamente Consistência, Disponibilidade e Tolerância a Partições — é preciso escolher trade-offs conforme o caso de uso. Um sistema de monitoramento IoT, por exemplo, geralmente prioriza disponibilidade (receber dados o tempo todo) em detrimento de consistência absoluta e imediata.

Como esses conceitos se conectam ao restante da disciplina

  • Os brokers de mensageria (MQTT, RabbitMQ, Kafka — Módulo 6) resolvem concorrência ao enfileirar mensagens, e escalabilidade ao permitir múltiplos consumidores/produtores.
  • As APIs REST/GraphQL (Módulos 4 e 7) são a materialização prática da openness.
  • O banco NoSQL e InfluxDB (Módulo 7) aplicam sharding/replicação para armazenamento em grande escala.
  • O Projeto Integrador (Semana 40) é, na prática, um sistema distribuído completo: vários dispositivos IoT concorrentes, publicando por protocolo aberto (MQTT), consumidos por um backend escalável.

💪 Atividades Práticas

🔬 Atividade 1: Simulando Concorrência com Sensores IoT

Implemente uma pequena aplicação que simule múltiplos sensores enviando leituras simultaneamente, evidenciando o problema de condição de corrida e sua solução.

📋 Instruções:

  1. Crie uma variável compartilhada (ex.: contador de leituras total)
  2. Simule 10 "sensores" (threads, processos ou promises) escrevendo nessa variável ao mesmo tempo, sem proteção
  3. Rode várias vezes e demonstre que o resultado final varia (a condição de corrida)
  4. Corrija o problema usando lock/mutex (ou uma fila) e demonstre que o resultado passa a ser sempre consistente
  5. Documente a diferença observada antes e depois da correção
📦 Entregável: Código-fonte comentado + print/relatório comparando os dois cenários

✅ Critérios de Avaliação:

  • Demonstração clara da condição de corrida
  • Correção funcional aplicada corretamente
  • Qualidade da explicação técnica

🔓 Atividade 2: Auditoria de Openness

Analise o projeto integrador (ou outro sistema real) sob a ótica de abertura/interoperabilidade.

📋 Instruções:

  1. Liste todos os protocolos e formatos de dados usados no seu projeto (MQTT, REST, JSON etc.)
  2. Para cada um, indique se é um padrão aberto ou proprietário
  3. Identifique pontos de "vendor lock-in" (dependência de um único fornecedor) se existirem
  4. Proponha alternativas abertas para eventuais pontos fechados
📦 Entregável: Relatório curto (1-2 páginas) com a auditoria

✅ Critérios de Avaliação:

  • Cobertura completa dos protocolos usados
  • Justificativa técnica correta sobre abertura
  • Qualidade das propostas de melhoria

📈 Atividade 3: Debate — Teorema CAP e Escalabilidade

Discussão em grupo sobre trade-offs de escalabilidade aplicados a um sistema IoT em larga escala.

📋 Instruções:

  1. Forme grupos de 4-5 alunos
  2. Cada grupo recebe um cenário (ex.: 1 milhão de sensores enviando dados por minuto)
  3. Discuta se o sistema deve priorizar Consistência ou Disponibilidade (CAP)
  4. Proponha uma estratégia de escalabilidade horizontal para o cenário
  5. Apresente as conclusões para a turma
📦 Entregável: Slide/documento com a decisão do grupo e justificativa

✅ Critérios de Avaliação:

  • Coerência técnica da decisão CAP
  • Viabilidade da estratégia de escalabilidade proposta
  • Clareza na apresentação
